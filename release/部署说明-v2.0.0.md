# 导航站 v2.0.0 部署说明

**状态：✅ 已于 2026-09-14 11:10 部署到生产并通过验收。** 本文档既是本次部署记录，也是以后重装/迁移的操作手册。

目标站点：`/www/wwwroot/nav/`（宝塔 · Nginx 1.22.1 · **PHP 8.2.28** · SQLite）
部署包：`nav-v2.0.0-deploy.zip`（约 200 KB）

> **只有四件事必须记住**，任何一件漏掉都会「看起来成功了，其实没生效」：
> 1. `.user.ini` 有 **immutable 属性**，不改属性写不进去（而且**不报错**）
> 2. **必须预建 `/www/wwwroot/nav-data` 并 `chown www:www`** —— open_basedir 是白名单，**不授予写权限**
> 3. `open_basedir` 里要带 **`/proc/`**，否则系统监控整页失效
> 4. 前端产物要**摊平**到站点根，**别把整个项目目录传上去**

---

## 0. 这次交付了什么

| | v1（旧） | v2.0.0（新） |
| --- | --- | --- |
| 前端 | 原生 JS，`index.html` + `admin.html` + `login.html` | Vue3 + Vite 构建的 SPA，单 `index.html` |
| 路由 | 多页面跳转 | Hash 路由（`#/admin`），**不需要改 nginx** |
| 后端 | `api.php` 单体 switch | `api/` 模块化 + 统一入口 `api/index.php` |
| 数据库 | `data.db` **放在站点根**（可被匿名下载） | 移到站点根**同级目录**，HTTP 访问不到 |
| 前台 | 只有后台能增删改 | **前台可直接添加/编辑/拖动排序** |
| 版本号 | 无 | 底部版本号 → 更新记录页，已写入 v2.0.0 内容 |

前端页面：`#/`首页 · `#/login`登录 · `#/changelog`更新记录 · `#/admin`后台（站点/分组/外观/账号/用户/备份/系统/版本）

## 1. 先备份（必须）

```bash
cd /www/wwwroot
TS=$(date +%Y%m%d_%H%M%S)
tar czf /www/backup/nav-current-$TS.tar.gz \
  --exclude='nav/frontend/node_modules' \
  --exclude='nav/.workbuddy' nav
# 关键数据单独再存一份
mkdir -p /www/backup/nav-data-$TS
cp -v nav/data.db nav/data.json nav/.user.ini /www/backup/nav-data-$TS/
```

> ⚠️ **备份时必须排除 `node_modules` 和 `.workbuddy`**，否则压缩包会到 300 MB 以上。

## 2. 上传并解包

把 `nav-v2.0.0-deploy.zip` 传到 `/www/wwwroot/`，然后：

```bash
cd /www/wwwroot/nav
unzip -o /www/wwwroot/nav-v2.0.0-deploy.zip
find /www/wwwroot/nav -mindepth 1 ! -name '.user.ini' -exec chown www:www {} +
```

> ⚠️ **不要用 `chown -R`** —— `.user.ini` 带 immutable 属性，`chown -R` 会中途报错并中断脚本
> （`set -e` 下会导致后续步骤全部不执行）。用上面这条 `find ... -exec`。

**注意：这里故意「不删旧文件」。** 旧的 `data.db` 是待迁移的数据源，第 4 步的自动迁移要从它复制。删早了数据就没了。

解包后站点根应该长这样（旧的 `api.php` / `admin.html` / `login.html` / `data.db` / `data.json` 先留着）：

```
/www/wwwroot/nav/
├── index.html          ← 已被 v2 覆盖（2119 字节）
├── assets/             ← 新增（vite 构建产物，36 个文件）
├── 48x48.ico  404.html
├── api/  config/       ← 新增（v2 后端）
├── uploads/  test/
├── .user.ini           ← 已被 v2 覆盖，第 3 步的重点
├── api.php  admin.html  login.html   ← 旧，第 5 步删
└── data.db  data.json                ← 旧，第 4 步迁移源，第 5 步删
```

### ⚠️ 如果你不是用这个 zip，而是手工上传

**必须把 `dist/` 里的东西摊平到站点根**：

```bash
cd /www/wwwroot/nav
cp -rv dist/index.html ./index.html
cp -rv dist/48x48.ico  ./48x48.ico
rm -rf ./assets && cp -rv dist/assets ./assets
```

**绝对不要**把本地整个项目目录（含 `frontend/`、`.workbuddy/`、`release/`、源码压缩包）传上来 ——
它们全都在站点根下，**任何人都能下载**。2026-09-14 实测过一次误传：站点根膨胀到 340 MB，
其中 `.workbuddy/` 242 MB（全部开发记忆与文档）、`frontend/` 60 MB（含 node_modules）、`nav.rar` 37 MB（整站源码）。

## 3. 🔴 `open_basedir` 与数据目录（最容易白做的一步）

v2 把数据库放到 `/www/wwwroot/nav-data/data.db`，也就是站点根的**同级目录**。
这里有两个独立的关卡，**必须都过**，只过一个是无效的：

### 关卡 A：`open_basedir` 白名单

宝塔默认只放行站点根：

```
open_basedir=/www/wwwroot/nav/:/tmp/
```

同级目录不在白名单里，PHP 直接拒绝访问。

### 关卡 B：文件系统写权限

`/www/wwwroot` 的属主是 **root**，PHP-FPM 以 **www** 运行 —— **www 没有权限在里面创建子目录**。

> 这条最容易被忽略：`open_basedir` 只是**白名单，不授予任何权限**。
> 白名单放行了，权限不够照样失败。

### 两个关卡任一没过，后果一样

`Db::resolveDbFile()` 会**静默退回**站点根内的 `storage/data.db` ——
**程序不报错、页面正常**，但数据库又变成 `http://站点/storage/data.db` 可匿名下载，等于漏洞只换了个文件名。

正确做法：

```bash
# 1) 预建站外数据目录并授权（解决关卡 B）
mkdir -p /www/wwwroot/nav-data
chown www:www /www/wwwroot/nav-data
chmod 750 /www/wwwroot/nav-data

# 2) 改 .user.ini（解决关卡 A）—— 注意 immutable 属性
F=/www/wwwroot/nav/.user.ini
chattr -i "$F"      # ← 不解除这个属性，写入会失败且只报「不允许的操作」
printf '%s\n' \
  'open_basedir=/www/wwwroot/nav/:/www/wwwroot/nav-data/:/proc/:/tmp/' \
  'display_errors=Off' > "$F"
chown root:root "$F"
chmod 644 "$F"
chattr +i "$F"      # 恢复宝塔的防篡改保护

cat "$F"

# 3) 让 PHP 重新读 .user.ini（宝塔默认缓存 300 秒）
/etc/init.d/php-fpm-82 reload
```

期望输出（两行）：

```
open_basedir=/www/wwwroot/nav/:/www/wwwroot/nav-data/:/proc/:/tmp/
display_errors=Off
```

**为什么要有 `/proc/`**：系统监控（CPU / 内存 / 磁盘）靠读 `/proc`。
`System::supported()` 判断的就是 `is_dir('/proc') && is_readable('/proc/stat')` ——
没放行就整页显示「系统监控不可用」。这是**只有生产才暴露**的问题：
本地 `php -S` 根本不读 `.user.ini`，测不出来。

**`display_errors=Off` 是额外保险**：生产 `php.ini` 里 `display_errors = On` 且
`error_reporting = E_ALL & ~E_NOTICE`，PHP 8.2 下 deprecation 警告会插在 JSON 前面把接口打坏。
（代码里 `bootstrap.php` 也自己关了一次，这里是双保险。）

### 如果 `.user.ini` 老是变回去

说明宝塔在接管它（在面板里点过「防跨站攻击」开关就会重写）。
去 `网站 → nav → 设置 → 网站目录 → 防跨站攻击(open_basedir)`，
把路径改成 `/www/wwwroot/nav/:/www/wwwroot/nav-data/:/proc/:/tmp/`。

## 4. 触发迁移并自检

浏览器打开一次站点（随便哪个页面），让后端跑一遍自动迁移。然后：

```bash
ls -lh /www/wwwroot/nav-data/data.db          # 应该在，约 120 KB
ls -lh /www/wwwroot/nav/storage 2>/dev/null || echo "好：站点根内没有 storage/"
```

**再进后台确认一遍**：登录 → `#/admin/system` → 看「存储与安全」卡片：

- 徽标显示 **数据库在站点根之外** → 对了
- 提示 **仍有 v1 遗留的 data.db** → 正常，下一步去删
- 显示 **数据库在站点根之内** → 回第 3 步，两个关卡有一个没过

> 这张卡片**不依赖 `/proc`**，即使系统监控不可用也会显示 —— 它是安全检查，不该被监控问题连累。

## 5. 清理 v1 遗留文件

确认第 4 步数据没问题（首页站点、分组、图标都在），再删：

```bash
cd /www/wwwroot/nav
rm -f data.db data.json api.php admin.html login.html
ls -la
```

顺手把开发目录也清掉（如果你不小心传上来了）：

```bash
cd /www/wwwroot/nav
rm -rf frontend .workbuddy release .trae dist
rm -f nav.rar
du -sh .        # 清理后应该只有几百 KB
```

为什么必须删：

- `data.db` 含 `users` 表的 bcrypt 哈希 + 全部站点配置，实测 `http://站点/data.db`
  返回 **HTTP 200 + 完整 SQLite 文件**（61440 字节），任何人都能下载。
- `data.json`（26 KB）同理。
- 迁移是**复制**不是移动，所以旧库不会自动消失，必须手工删。

## 6. 加 nginx 兜底规则（已执行）

已写入宝塔的扩展配置目录（该目录会被站点配置自动 `include`，且宝塔不会清理）：

```bash
mkdir -p /www/server/panel/vhost/nginx/extension/nav
vi /www/server/panel/vhost/nginx/extension/nav/deny-sensitive.conf
nginx -t && nginx -s reload
```

内容：

```nginx
location ~* \.(db|db-wal|db-shm|sqlite|sqlite3|sql|bak|old|zip|rar|7z|tar|tgz|gz)$ {
    deny all; return 404;
}
location ~* /(storage|backup|\.git|node_modules)/ {
    deny all; return 404;
}
location ~* /(data\.json|package\.json|composer\.(json|lock))$ {
    deny all; return 404;
}
```

这条是**第二道防线**：万一 `open_basedir` 被重置、或以后又误传了源码包，也不会被下载。
主防线仍是第 3 步。

## 8. 回滚

```bash
cd /www/wwwroot
mv nav nav.v2fail
tar xzf /www/backup/nav-current-<时间戳>.tar.gz
find /www/wwwroot/nav -mindepth 1 -exec chown www:www {} +
rm -rf /www/wwwroot/nav-data
# 恢复 .user.ini 原内容（只有 open_basedir 一行、不含 -data 与 /proc/）
```

v2 不改动 v1 的任何表结构（迁移是加列 + 建新表，不 DROP），所以回滚后旧的 `api.php` + `data.db` 能正常跑。
