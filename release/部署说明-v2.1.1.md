# 导航站 v2.1.1 增量升级说明

从 **v2.1.0** 升到 **v2.1.1**。这是一个 bug 修复版，**不改数据库结构**，
回滚只需换回文件。

> 本次已经在生产 `192.168.0.116`（http://123.lan）完成部署并实测通过，
> 这份说明是留给以后重装/换机器时用的。

---

## 0. 这次改了什么

| 类型 | 内容 |
| --- | --- |
| 修复 | 「导入备份」选好 JSON 文件后，**「开始导入」按钮一直是灰的、点不动** |
| 优化 | 导出的备份文件改为**干净的备份本体**（以前多包了一层接口外壳） |
| 优化 | 解析失败时**直接在页面上写明原因**，不再只有按钮变灰 |
| 优化 | 导入时自动忽略 **UTF-8 BOM**（用记事本另存过的 JSON 也能识别） |

### 根因（值得记一笔）

导出接口 `backup.export` 返回的是：

```json
{ "file": "nav-backup-20260914-1301.json",
  "data": { "format": "nav-backup", "categories": [...], "sites": [...] } }
```

前端 `doExport()` 拿到的是整个返回值（= `{file, data}`），却直接
`JSON.stringify()` 下载了。于是**导出的文件顶层只有 `file` 和 `data`**，
真正的 `categories` / `sites` 被埋在里面一层。

而前端 `parseText()` 的校验是：

```js
if (!Array.isArray(d.categories) && !Array.isArray(d.sites)) throw ...
```

顶层没有这两个数组 → 抛错 → `payload` 保持 `null` → 按钮
`:disabled="importing || !payload"` **永远是灰的**。

有意思的是**后端本来就兼容**这种双层结构（`backup.php` 里有一段
`if (isset($raw['data']) && ...) $raw = $raw['data'];`），所以问题纯粹
卡在前端这一层校验上——后端根本没机会被调用。

### 修法

1. `doExport()` 里取出 `data` 再序列化，**新导出的文件是干净的**，
   同时沿用服务端给的 `file` 字段做文件名。
2. 新增 `unwrap()`：向下钻最多 3 层，兼容
   - 干净的备份对象
   - 旧的 `{file, data}` 外壳 —— **你手上那份文件现在能直接用了**
   - 手工包一层的 `{data: {...}}`
3. `parseText()` 增加 UTF-8 BOM 剥离，失败原因写进 `parseError` 并显示在页面上。
4. `doImport()` 兜底：粘贴完直接点按钮时（`change` 事件还没触发）自动补解析一次。
5. 按钮不可点时，旁边多一行灰字提示「先选择文件或粘贴内容，解析成功后按钮才可点」。

## 1. 覆盖文件

本次只动了 `api/`、`config/` 和前端产物，**不需要建目录、不需要改 `.user.ini`**。

```bash
SR=/www/wwwroot/123.lan

# 上传 release/123.lan-v2.1.1-deploy.zip 到服务器，然后：
cd /tmp && rm -rf nav211 && mkdir nav211 && unzip -q /path/to/123.lan-v2.1.1-deploy.zip -d nav211
cd nav211

# 后端 + 配置（cp -a api/. 是「覆盖内容」，不会先删目录，站点不会中断）
cp -a api/.    $SR/api/
cp -a config/. $SR/config/

# 前端产物「摊平」到站点根（老 assets 带 hash，直接整目录换掉）
rm -rf $SR/assets
cp -a assets   $SR/assets
cp -a index.html $SR/index.html

# 属主与权限
# ⚠️ 不要对 .user.ini 做 chown/chmod —— 它是 root + immutable(chattr +i)
find $SR -type d -exec chmod 755 {} \; 2>/dev/null
find $SR -type f -exec chmod 644 {} \; 2>/dev/null
chown -R www:www $SR/api $SR/config $SR/assets $SR/index.html

# 重载 PHP-FPM（清 opcache，并让 user_ini 缓存立即失效）
/etc/init.d/php-fpm-82 reload
```

> `find` 会对 immutable 的 `.user.ini` 报一条 Operation not permitted，**忽略即可**。

## 2. 验收清单

### ① 版本号

```bash
curl -s 'http://123.lan/api/index.php?action=home.index' | grep -o '"version":"[^"]*"'
# 期望： "version":"2.1.1"
```

### ② 前端产物已换新（旧的带 hash 文件应 404）

```bash
# 从 index.html 里取出实际引用的 assets
curl -s http://123.lan/index.html | grep -oE './assets/[A-Za-z0-9_.-]+\.(js|css)'

# 逐个确认 200；再随手试一个不存在的哈希，应为 404
curl -s -o /dev/null -w '%{http_code}\n' http://123.lan/assets/BackupView-C-r2jD5x.js   # 404
```

### ③ 核心回归：旧格式的备份文件也能导入（浏览器里点，不要只测接口）

这一步**必须走浏览器**，因为坏的是前端校验，接口一直是好的。

1. 打开 `http://123.lan/#/admin/backup`
2. 点「选择 JSON 文件」，选**你之前导出的那份** `nav-backup-20260914-1301.json`
3. 期望：
   - 下方出现「已解析：N 个分组、M 个站点」
   - **「开始导入」按钮变成可点的紫色**（修复前是灰的）
4. 点「开始导入」→ 确认框再点一次 → 底部出现「新增 …」的结果框

### ④ 无效文件必须有明确报错（不能静默失败）

随便选一个 `.json` 但内容不是备份（例如 `{"hello":"world"}`），期望页面上
出现红字「解析失败：备份里既没有 categories 也没有 sites」，按钮保持灰色。

### ⑤ 敏感路径复查（应全 404 / 403）

```bash
for p in data.db storage/data.db 123.lan.rar api/bootstrap.php .user.ini \
         config/config.php data.json api.php admin.html login.html; do
  printf '  %s  /%s\n' "$(curl -s -o /dev/null -w '%{http_code}' --max-time 6 http://123.lan/$p)" "$p"
done
# 期望：.db/.json/v1 遗留 全 404；api/bootstrap.php 与 config/config.php 是 403
#       （403 是 PHP 内部的 NAV_ENTRY 守卫，不是泄露）
```
